# Skill: ingest-note

Process raw notes from `../inbox/raw/` into draft pages in `../inbox/staging/`. Nothing reaches the wiki repo until the contributor explicitly runs the share skill. `../inbox/` is a plain local folder, not a git repo. Apart from the wiki sync in step 0, this skill does not fetch, merge, commit or push anything.

## When to use

Run this skill when the contributor wants to bring new inbox items to staging, or when a specific raw note needs to go into the staging layer.

## Input

- The path to the local inbox: `../inbox/raw/`
- Optional: a specific file
- **Contributor name** — for `contributed-by` in the frontmatter of the new pages. Web Clipper notes already supply this via the `contributor:` field in their frontmatter (filled in by the personal clipper template). For manual notes: ask if it cannot be inferred from context (an earlier session in this conversation).
- **anonymize** — optional. Default: no. Only apply when the contributor explicitly asks for it.

## Input types

Files in the inbox come from three sources. Recognize them by extension and frontmatter:

**Obsidian Web Clipper** (primary source for web content)
Generated by the clipper template. Recognizable by `tags: [clippings]` and a `source:` URL. Also contains `context: webclipping`, `author:`, `published:`, `created:`. Treat them as research, unless the content clearly describes a project or decision.

**Manual notes** (meeting minutes, ideas, decisions)
Written directly in Obsidian or another editor. May contain `context:`, `type:` and `share:`.

**Binary documents** (`.docx`, `.pdf`, `.pptx`, `.xlsx`)
Placed in the inbox locally, never committed. Step 2 converts them to markdown before they are processed further.

## File name sanitization

Every file name this skill creates or moves (in `processed/`, `staging/`, or derived from a title/slug) must not contain characters that are not allowed on Windows: `< > : " / \ | ? *`, and must not end in a period or space. A file with such a character breaks `git clone` on Windows.

Apply this:
- When deriving a slug from a title (step 4): replace illegal characters with nothing or a hyphen, and collapse consecutive hyphens.
- When moving the original file to `processed/` (step 5): if the inbox file name (e.g. a Web Clipper title) contains illegal characters, sanitize the name while moving. The title in the frontmatter or text stays unchanged, only the file name is adjusted.

## Steps

### 0. Sync the wiki with main

Make sure you have the latest version of the wiki. Merge any curator changes before creating staging.

```bash
git fetch origin
git merge origin/main
```

On merge conflicts: resolve them before continuing. `../inbox/` has no git and so needs no sync step.

### 1. Discover inbox files

List all files in `../inbox/raw/`, including binary formats (`.docx`, `.doc`, `.pdf`, `.pptx`, `.ppt`, `.xlsx`, `.xls`). Skip files that are already in `../inbox/processed/`.

### 2. Convert binary files to markdown

Convert each binary file from step 1 to markdown with pandoc before continuing:

```bash
pandoc "<input>" -t markdown -o "<input-without-extension>.md"
```

Per format:
- **docx** — good quality; tables, headings and lists come through well
- **pdf** (text-based) — reasonable; may need some cleanup
- **pptx** — text only; slides become sections
- **xlsx** — tables only, no formulas

After a successful conversion:
- Add minimal frontmatter to the generated `.md` if it is missing:
  ```yaml
  ---
  date: YYYY-MM-DD
  context: converted-document
  original-file: <original file name with extension>
  ---
  ```
- Move the binary original to `../inbox/processed/` (stays local).
- Process the `.md` further like an ordinary inbox file.

If pandoc fails (e.g. a scanned pdf without a text layer), skip the file and report it in the summary as `SKIPPED (conversion failed — <reason>)`.

### 3. Read and interpret the file

Determine what the file is. First read `schema/structure.json`: it contains this team's content types (folder, description, template, required fields). The types below (project, decision, ways of working) are the standard template; if the team has chosen other types, use those. If the file fits no type, ask the contributor where it should go.

**Project** — about an existing or new project in `wiki/projects/`.

**Decision** — frontmatter contains `type: decision`, or the content clearly describes a decision (go, no-go, park, stop).

**Ways of working** — describes how the team works: process, roles, agreements, principles or guides. Goes in `wiki/ways-of-working/`.

**Research or general insight** — a research note, report or background that belongs to a project. Goes in `wiki/projects/<slug>/research/`. If it belongs to no project, ask the contributor where it should go.

### 4. Create draft pages in staging

Create draft pages in `../inbox/staging/` that mirror the final wiki folder structure. For example:

```
../inbox/staging/projects/llm-wiki/index.md              →  wiki/projects/llm-wiki/index.md
../inbox/staging/projects/llm-wiki/research/2026-07-28-market.md  →  wiki/projects/llm-wiki/research/...
../inbox/staging/decisions/2026-07-29-llm-wiki-start-pilot.md     →  wiki/decisions/...
../inbox/staging/ways-of-working/meeting-structure.md              →  wiki/ways-of-working/meeting-structure.md
```

Use the template that belongs to the type: the `template` field of the type in `schema/structure.json` (by default `schema/project-template.md` and `schema/decision-template.md`). Also fill in the fields from `fields`. If the type's `description` mentions special rules, for example for personal data, follow them.

Set `status: draft` on all pages. Do NOT write to `wiki/` in this step.

**For decisions: also work through the consequences** (only if the team has a decision type that refers to a case; for other types: update the related case and the index in the same way, using the status transitions the team has defined)

The decision document alone is not enough. After writing `../inbox/staging/decisions/<file-name>.md`, also apply the decision to the project and the index in staging:

1. **Determine slug and decision** from the frontmatter (`project:`, `decision:`) or derive them from the text.
2. **Find the project page in staging** at `../inbox/staging/projects/<slug>/index.md`. If it is missing, first copy `wiki/projects/<slug>/index.md` to staging. If that does not exist either, create a minimal stub based on `schema/project-template.md`.
3. **Update the project page in staging:**
   - `status` according to the decision: `go` → `active`; `park` → `paused`; `stop` → `stopped`; `no-go` and `adjust` → leave `status` unchanged
   - `date-updated` → today
   - add a row to the table under History
   - add a link to the decision document under Decisions
4. **Update the index in staging** at `../inbox/staging/index.md` (copy from `wiki/index.md` if it is missing): the project's row (latest decision, status), or a new row if the project is not in it yet.

For new projects: also add a row to `../inbox/staging/index.md`.

**Anonymization (only if the contributor requested it):**

If the contributor specified `anonymize`:
- Scan the text for recognized names (use `contributed-by` values as a starting point, plus names in the source files).
- Replace names found with a generic role description (e.g. "Jan de Vries" → "the project lead"). If the role cannot be inferred, use "a team member".
- Add to the frontmatter: `anonymization-status: anonymized`
- Note in the summary (step 6) which names were replaced.

If `anonymize` was not specified: leave the text unchanged and do not add an anonymization status.

### 5. Archive the original source

Move the original inbox file (the unchanged `.md` note, or the binary original already moved in step 2) to `../inbox/processed/` (create the folder if it is missing), so that `raw/` only contains files that still need processing. Never delete raw files. `processed/` is local only. The draft pages from step 4 also stay local in `../inbox/staging/` until the contributor runs `share`.

Apply the file name sanitization to the file name before moving.

```bash
mkdir -p ../inbox/processed/
mv "../inbox/raw/$(basename "$file")" "../inbox/processed/"
```

### 6. Show a summary

Give the contributor an overview:

```
Ingest complete. The following draft pages are ready in staging:

- staging/projects/llm-wiki/index.md  →  wiki/projects/llm-wiki/index.md  [anonymized: Jan de Vries → "the project lead"]
- staging/decisions/2026-07-29-llm-wiki-start-pilot.md  →  wiki/decisions/...
- ...

Skipped: <list with reason>

Review them in Obsidian via the inbox vault (../inbox/).
When you are ready to share, say: "run the share skill".
```

Only mention anonymization information if the contributor asked for it: which names were replaced and by which role.

## Edge cases

- **Unclear which project a note belongs to:** create staging pages for both projects and put a remark at the top of each page that the contributor must decide before sharing.
- **No clear project:** create a staging page in `../inbox/staging/unknown/` and report this in the summary.
- **Duplicate content:** if the note largely repeats an existing staging or wiki page, add a short remark to the existing staging page instead of creating a new one.
- **Staging file already exists:** add the new content to the existing staging page instead of overwriting it.
